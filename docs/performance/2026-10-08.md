# Local-model performance — 8 October 2026

## Decision

Retain the existing llama.cpp cache, checkpoint and batch defaults on both profiles. The M1 measurements rejected cache disabling and batch-size changes; the M4 Pro has not been measured. The opt-in lean Qwen profile reduced median coding-session time by 46.9% on the disposable M1 fixture, with all six sessions passing correctness checks. No backend or model changed.

## M1 16 GB: server matrix

Apple M1, 16 GiB unified memory; llama.cpp 0.6.0, build 11429, commit `d81235049`; Qwen3.5-9B UD-Q4_K_XL (6.0 GB file). Full 33/33-layer Metal offload was confirmed. Context 65536, flash attention on, one slot, logical batch 2048, f16 KV. Three repetitions per scenario; 2048-token synthetic code fixture, up to 16 generated tokens, temperature 0, seed 42. The formatted chat prompt includes additional template/tool tokens.

| Variant | Median request | Change vs baseline | Return to main | Swap growth | Tool call |
|---|---:|---:|---:|---:|---|
| baseline | 13.11 s | +0.0% | 2.53 s | 2110 MiB | pass |
| bounded-8 | 24.21 s | +84.7% | 25.41 s | 0 MiB | pass |
| bounded-32 | 25.28 s | +92.9% | 26.39 s | 0 MiB | pass |
| batch-256 | 13.36 s | +1.9% | 2.63 s | 1640 MiB | pass |
| batch-1024 | 14.55 s | +11.0% | 2.60 s | 876 MiB | pass |

Baseline: cache ceiling 8192 MiB, 32 checkpoints, physical batch 512. Bounded-8 and bounded-32 disable host cache and keep the indicated checkpoint count. Batch variants retain baseline cache/checkpoints. All structured `read_file` calls parsed successfully; these tests did not execute tools.

Baseline scenario medians:
- cold: first token 22.51 s, total 24.11 s, prompt 105.8 tokens/s, generation 9.4 tokens/s, cached tokens 0.
- growing: first token 0.85 s, total 2.32 s, prompt 48.8 tokens/s, generation 9.5 tokens/s, cached tokens 2341.
- branch: first token 22.13 s, total 23.72 s, prompt 106.8 tokens/s, generation 9.6 tokens/s, cached tokens 0.
- return: first token 0.94 s, total 2.53 s, prompt 48.2 tokens/s, generation 9.4 tokens/s, cached tokens 2377.

Disabling host cache preserved linear follow-up reuse but lost return-to-main restoration. It made that scenario roughly ten times slower. The baseline cache held about 2.2 GiB of prompt states by the end of this synthetic switching workload; individual recurrent checkpoints measured about 50.25 MiB. An 8 GiB cache limit is not an immediate allocation of 8 GiB.

Swap numbers are system-wide growth after server startup, not process-owned bytes. The machine already had several GiB of swap in use; other applications remained running. Variant order and thermal/system load can affect comparisons. The small fixture does not establish performance at 16k–64k active context. No candidate met the required 10% latency improvement; no default was changed on the strength of a memory reduction alone.

## Bounded-cache follow-up

A fresh comparison tested a 1024 MiB host cache with 8 checkpoints against baseline. This retained cached restoration, but missed the latency target:

| Variant | Median request | Return to main | Swap growth | Tool call |
|---|---:|---:|---:|---|
| baseline | 14.48 s | 2.80 s | 1210 MiB | pass |
| cache-1024 | 14.77 s | 3.20 s | 152 MiB | pass |

The bounded cache reduced swap growth and preserved returns on this short fixture, but was slower under the measured system load. It remains an explicit experiment (`lca config set CACHE_RAM 1024` and `lca config set CTX_CHECKPOINTS 8`), not a changed default. Longer histories may require more cache space. ## Qwen Code profile

Installed version: 0.25.0. The lean profile disables automatic memory extraction, dreaming, skill review, workflows, and the registered `agent` tool; it keeps six file/search/shell tools eager and preserves the discovery bridge and unrelated settings. Unit tests cover restoration, intervening edits, invalid settings, provider sync, and repeated application. The installed command and updater were also exercised with disposable HOME/XDG directories.

The earlier local usage log contained 20 calls to Qwen3.5-9B: 11 main, 4 Explore, and 5 managed-auto-memory-extractor calls. The memory calls had summed recorded API durations of 176.9 seconds. These durations include waiting and may overlap; they are not an estimate of wall-clock savings.

The corrected comparison alternated normal/lean order across three repetitions, using fresh HOME/XDG directories and disposable projects on one isolated Metal server. Each session found and fixed an addition function, discovered the deferred `web_fetch` schema without invoking it, created three unit tests, and ran them. Both profiles used the same provider, 65536-token context, production sampling, thinking disabled, and a 512-token response cap. Full 33/33-layer GPU offload was confirmed.

| Profile | Session times | Median session | Median first prompt | Main / memory requests | Correctness |
|---|---|---:|---:|---|---|
| normal | 309.7 / 374.6 / 342.7 s | 342.7 s | 15,746 tokens | 6 / 1 each | 3/3 pass |
| lean | 176.6 / 181.9 / 193.7 s | 181.9 s | 10,294 tokens | 6 / 0 each | 3/3 pass |

Lean reduced median full-session latency by **46.9%** and the initial prompt by **34.6%**. Median summed main-request API duration was 250.0 seconds for normal and 180.1 seconds for lean. Normal also made one automatic memory-extraction request per session, with a median recorded API duration of 86.8 seconds; lean made none. API durations include prefill and waiting, so they are not decode-speed measurements. No subagent was invoked in either profile.

All six sessions recorded successful shell execution and tool discovery, exited successfully, and passed independent positive/negative/zero addition checks plus the three generated unit tests. The `agent` tool was registered only in normal; shell and the discovery bridge were registered in both. This establishes the improvement on this small fixture, not on long coding tasks or the M4. System load, model output variation, and thermal effects remain uncontrolled. Lean stays opt-in.

An initial headless probe hid the shell tool in both profiles: the command-scoped permission did not register it in headless mode. Its timings are excluded. The corrected fixture uses a core-tool registration allowlist with the same narrow command permission; the benchmark rejects assistant execution claims without recorded successful shell/discovery calls. User permissions and settings were not changed.
