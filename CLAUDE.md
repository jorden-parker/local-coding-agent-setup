# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`setup.sh` is the single install-and-update command: it fast-forwards this checkout (re-executing itself when commits arrive), installs or upgrades llama.cpp, hf and Go with Homebrew, downloads a Qwen GGUF model to `~/models` unless config.env already points at one that exists, seeds `~/.config/llama-coder/config.env`, installs the two static launchers from `launchers/` to `~/.local/bin` (`local-harness` plus `qwen-local` and `pi-local` symlinks to it), builds the Go tool `lca` (`cmd/lca`, `internal/`) there too, and runs `lca sync` to merge the local provider entry into each harness's own configuration, then `lca doctor` (a doctor failure makes setup.sh exit non-zero). There is no separate updater; re-running setup.sh is the update. `lca` edits config.env, patches the harness configuration, and summarises response times (CLI subcommands and a Charm TUI). `README.md` documents it. `.claude/` holds the check hook and the `/sync-readme` skill. macOS on Apple Silicon only.

Two agent harnesses are supported: Qwen Code and pi (https://pi.dev). **setup.sh installs neither** — pi has no Homebrew formula and self-updates with `pi update`, and Qwen Code is left to the user because lca patches the configuration file a harness already owns and so must not be in the business of installing or replacing one. The launchers and `lca doctor` only check and hint. Nothing may fail or even report a check when a harness is absent unless `HARNESS` selects it; the work machine has only Qwen Code.

lca owns no harness configuration of its own. `lca sync` merges one provider entry into `~/.qwen/settings.json` and `~/.pi/agent/models.json` (or wherever `QWEN_HOME`/`PI_CODING_AGENT_DIR` point) and writes nothing else; `internal/backup.Once` copies each file aside before the first write; `lca unsync` takes the entry back out. Writing less is the governing constraint here: every key lca adds is one the user did not ask for, and `app.Syncs` exists so that merely installing a harness is not an invitation into its configuration.

## Never run setup.sh or the installed launchers

setup.sh runs `git pull --ff-only` on this checkout, downloads ~22 GB, runs `brew install`/`brew upgrade`, and overwrites `~/.local/bin/{llama-coder,local-harness,qwen-local,pi-local,lca}` without asking. Worse, against the real HOME, `lca sync`, `lca unsync`, `lca qwen-profile`, `lca config set`, `lca config edit` and the TUI's Config tab now write the real user's **own** harness configuration — `~/.qwen/settings.json` and `~/.pi/agent/models.json` — not a copy lca owns. Verify changes statically only:

```bash
bash -n setup.sh && shellcheck setup.sh launchers/llama-coder launchers/local-harness .claude/hooks/check.sh
gofmt -l . && go vet ./... && go test ./...
```

All must pass clean before you are done. A hook runs the relevant checks after every edit to a `.sh`, `launchers/*`, or `.go` file. `go build`, `go test`, and `go vet` are safe. For manual checks of `lca` or the launchers, set `HOME`, `XDG_CONFIG_HOME`, and `XDG_STATE_HOME` to a temp dir first, build the binary before changing `HOME` (a `go run` under a temp HOME downloads a module cache there), and put stub `llama-server`/`llama-coder`/`qwen`/`pi`/`curl` scripts on PATH (the launcher starts `llama-coder` itself; see the stubs in `internal/cli/launchers_test.go`).

To check a Homebrew package, use `brew info <formula>` (read-only). Never `brew install` from here.

## Launchers and config.env

`launchers/llama-coder` and `launchers/local-harness` are plain bash, installed verbatim with `install -m 755`; `qwen-local` and `pi-local` are `ln -sfn` symlinks to the installed `local-harness`. Nothing is baked in at setup time; both scripts `source` config.env at every start.

- `local-harness` picks the harness from the name it was invoked under (`${0##*/}`: `qwen-local` or `pi-local`), then `HARNESS=` in the environment, then config.env's `HARNESS`, then `qwen`; anything else is an error. Everything up to and including port selection is harness-agnostic; `prepare_qwen`/`prepare_pi` and `exec_qwen`/`exec_pi` hold the rest, dispatched by an explicit `case` (shellcheck's SC2329 flags `"prepare_$harness"` as an uninvoked function). Each `prepare_` requires its binary on PATH and otherwise exits with that harness's install hint *before* any sync; keep those two hint strings identical to `qwenInstallHint`/`piInstallHint` in `internal/app`, which `internal/cli/launchers_test.go` asserts. The harness runs as a foreground child so the EXIT trap still stops a server this session started.

- `CTX=` and `PORT=` in the environment win over the file for that run (the launchers save them before sourcing). `local-harness` manages its own server: without `PORT=` it claims the first port from config.env's `PORT` upward not held by another live session (claim = `$XDG_STATE_HOME/llama-coder/instances/<port>/owner.pid`, created by hard-linking a temp file so concurrent launches cannot both win), then adopts a server answering `/health` (waiting on 503), starts `PORT=<port> llama-coder` in the background when nothing listens (`server.pid`, `launcher.log`), and its EXIT trap stops only a server it started or adopted from a dead claim. `PORT=` pins the port and shares it if another live session holds it (`sharers/<pid>`). The harness runs as a foreground child, not `exec`, so the trap runs; `&` children would have SIGINT ignored.
- **The launcher must not move `QWEN_HOME` or `PI_CODING_AGENT_DIR`.** Those are where each harness reads the configuration, memory, sessions and IDE lock that `lca sync` patches and `lca stats` reads, so `internal/paths.QwenDir`/`PiDir` honour them (absolute values only, like `xdg()`); redirecting one would patch one file while the harness read another. There is no `qwen-<port>`/`pi-<port>` scheme and no `ide/` symlink any more: Qwen Code finds the VS Code companion's `<port>.lock` in its own `ide/` because the variable is left alone. `PI_CODING_AGENT_SESSION_DIR` *is* still unset, because it moves the sessions out from under `PiDir()` and so out of reach of `lca stats`.
- `pi-local` runs `pi --provider llama-local --model "$ALIAS"`. That provider id is `internal/pi.ProviderID` and the two must stay equal. pi's `settings.json` is never written: `defaultProvider`/`defaultModel` are the user's selection and these flags make them unnecessary. Do not switch to pi's own llama.cpp integration (`LLAMA_BASE_URL`, `/llama`): it needs llama-server in router mode, which `llama-coder` does not start.
- The launcher always calls `lca sync --harness <harness> --port "$PORT"`. Keep `--port`: pi has **no base-URL flag**, so `providers.llama-local.baseUrl` in `models.json` is the only way it learns which port to call, and a session on an auto-walked port would otherwise reach the wrong server. It is a plain runtime override now (`f.Set` without saving), so there is no port-override detection to get right. Without `--harness`, `lca sync` patches every harness `app.Harnesses` returns. The launcher tests run through a symlink named `qwen-local`/`pi-local` so the `$0` dispatch is exercised, and assert that both harness home variables come through *unchanged*.
- A llama-server whose Metal backend has failed a command buffer cannot be recovered in process and answers every request with "Compute error", while `/health`, `/slots` and `/metrics` all keep reporting it healthy (checked against a live wedged server). `instances/<port>/launcher.log` is the only signal, so the launcher greps it before adopting a server and keeps watching it for the rest of the session. The marker lives twice, as `WEDGED_MARKER` in `local-harness` and `server.WedgedMarker` in Go; `internal/app.TestWedgedMarkerMatchesTheLauncher` pins them together, and both must stay in step with llama.cpp's own wording. When the walk skips a wedged server it stops it first (`stop_inherited`): on a 16 GB machine two servers do not fit, so leaving it would OOM the replacement. The background watcher must be reaped with `pkill -P` before `kill`, because the `sleep` it blocks on is a separate process that inherited the session's stderr.
- `app.Syncs(f, h)` is the one gate on whether lca touches a harness's configuration: `HARNESS` selects it, or its configuration already carries the local provider (`qwen.Entry`, `pi.HasProvider`) from an earlier sync. Do **not** widen this to `exec.LookPath`: that would make installing pi for cloud work mean `lca config set PORT` silently rewrites `~/.pi/agent/models.json`. Both harnesses get the same treatment, including `addQwenChecks`/`addPiChecks`, which stay silent for an absent harness `HARNESS` does not select — setup.sh gates its exit code on `lca doctor`, so a pi-only machine must not see `FAIL qwen provider`.
- `lca sync` must never write the lean profile. It runs on every launch, and those settings change Qwen Code's behaviour for every model, so re-asserting them would override a deliberate `lca qwen-profile restore`. setup.sh applies lean once, gated on having just *written* config.env (`FRESH_CONFIG`) — not on the snapshot's absence, which only means "lean is not applied right now". `lca doctor` reports the profile as a warn at most, never a `FAIL`.
- `Unprepare`/`UnprepareModels` remove only what still matches what lca would write (`editedFields`, `extraKeys`), report anything edited in `Removal.Left`, and never touch a real `env.OPENAI_API_KEY`. `app.deleteIfOurs` deletes a configuration file outright only when it is empty *and* no backup exists — the absence of a backup is the proof lca created the file, since `backup.Once` takes one whenever the file was already there.
- setup.sh writes config.env only when absent and never overwrites it. The memory-profile defaults (`MEM_GB < 24` → Qwen3.5-9B, `CTX=65536`; otherwise Qwen3.6-35B-A3B, `CTX=131072`) only seed that first file; memory detection must stay above the defaults block. Moving to a new machine with an existing config.env keeps the old values, and setup.sh prints the diff.
- `qwen-local` selects Qwen Code's OpenAI-compatible provider via `OPENAI_API_KEY` (any value), `OPENAI_BASE_URL` (must end in `/v1`), and `OPENAI_MODEL` (must equal `ALIAS`). Do not reintroduce `ANTHROPIC_*` or `CLAUDE_CODE_*` vars.
- macOS `/bin/bash` is 3.2: no `mapfile`, no `declare -A`, and empty arrays need `${arr[@]+"${arr[@]}"}` under `set -u`.
- No settings entry names a skills directory, and none should: `paths.QwenSkillsDir`/`PiSkillsDir` and `AgentsSkillsDir` are all roots the harness resolves from its own home, so an entry would only duplicate what it already reads. `lca doctor`'s `qwen skills`/`pi skills` checks report both roots per harness through `app.addSkillsCheck`; the count is a floor, only good for telling an empty root from a populated one, because the roots overlap (a harness skills dir is commonly a symlink farm into `~/.agents/skills`).
- The key list, ranges, and which keys sync to a harness live in `internal/config/catalog.go`. Adding a key means: catalogue entry, the config.env heredoc in setup.sh, the launcher flag, the README key table. `HARNESS` is a `KindEnum` key with `Choices`; it has a `Default` so older config.env files without it still validate.

## Keep README.md in sync with setup.sh

Model repo/file/alias, default `CTX` and `PORT`, model file size, both memory profiles and the threshold that selects them, the config.env defaults and key table, the `llama-server` flags in `launchers/llama-coder`, the install list (Go, the launchers and their symlinks, and that *neither harness* is installed), the update steps (pull, package upgrade, model check, fresh-install lean, doctor), the `lca` command list, the Qwen settings and pi `models.json` keys `lca sync` writes, the backup filename, what `lca unsync` can and cannot undo, and the reasons for them appear in both files. Change both. Run `/sync-readme` to check.

## Conventions

- Comments on non-obvious flags cite the source (llama.cpp issue, Unsloth guide). Keep that when adding flags.
- Overridable settings use `${VAR:-default}` at the top of setup.sh and are documented in the header comment and README.
- Go: one package per harness (`internal/qwen`, `internal/pi`), both writing `internal/usage.Record` values that `internal/stats.FromUsage` buckets; `internal/app` chooses between them from `HARNESS` and `app.Source`. gofmt and `go vet` clean; Charm v2 imports (`charm.land/bubbletea/v2`, `bubbles/v2`, `huh/v2`, `lipgloss/v2`); every user-file write goes through `internal/atomicfile`; everything under `internal/` so nothing is importable; paths resolve through `internal/paths` at call time so tests can `t.Setenv`. `internal/app` is the layer shared by `cli` and `tui`; do not import `cli` from `tui`.
- The harness packages take paths as arguments and never import `internal/paths`, so deciding *which* file to patch — and taking the backup before it — belongs in `internal/app`. `go vet ./...` type-checks `_test.go` files, so a rename that collides with an existing name needs bodies repointed before names change, or every intermediate edit trips the hook.
- A settings file that is not strict JSON is refused with a message naming the file; do not strip comments to make it parse, because the round trip through a Go map would delete them for good. That round trip is also why the backup is mandatory rather than nice to have: `json.MarshalIndent` over a map sorts keys, so the first sync reorders the whole document even when the change itself is exactly reversible.
- Tests that touch files set `HOME`, `XDG_CONFIG_HOME`, and `XDG_STATE_HOME` to `t.TempDir()`.
